# Literature matrix: text classification for radio traffic

**Prepared:** 2026-11-24
**Scope:** Short, noisy radio transcript segments classified into operational call-type labels (fire, police, EMS, bus, school, traffic, electrical/utilities, and related categories). This review concerns text analysis after TRANS transcription; it does not recommend replacing transcription or human review.

## Evidence matrix

## Synthesis and recommended practice

1. **Model the task as multilabel triage.** A single segment may describe several services or concerns, such as a school bus incident affecting roadway traffic. A forced single class would discard that information. Define whether each label means a responding service, an incident subject, or an operational concern; these are different axes. The current labels mix these concepts, so the initial taxonomy should be treated as provisional.
2. **Separate source kind from semantic labels.** Only TRANS segments marked `speech` receive call-type labels. Audible events and uncertain segments remain distinct. Never rewrite source text to make a rule match.
3. **Treat current keyword rules as candidate indicators.** Keyword presence is not a validated incident classification. Ambiguous words (for example, “traffic” in “traffic stop”, or “school” as a location) can create false positives. A future schema should retain label evidence/spans, rule version, and a review state per label; aggregate counts alone cannot show why a rule fired.
4. **Create a domain-specific annotation guide before tuning rules.** Specify the unit (segment or whole call), multilabel policy, category definitions, exclusions, cross-category examples, and how to label incomplete/ASR-corrupted text. Have at least two reviewers annotate a stratified sample independently, resolve disagreement through adjudication, and preserve unresolved cases as ambiguous.
5. **Use leakage-resistant, source-grouped evaluation.** Keep segments from the same call/source together when creating development and held-out sets. Otherwise repeated station terms or near-duplicate calls can inflate results. Report dataset scope and distribution, including source type, transcript review state, and category support.
6. **Measure each label and failure mode.** Report per-label precision, recall, F1, and support plus micro/macro summaries. Inspect false positives and false negatives for rare labels. If probabilistic models are introduced, evaluate per-label calibration and define abstention/review thresholds from the cost of each error; do not trust self-reported model confidence by itself.
7. **Monitor vocabulary and domain shift.** Agency names, local codes, geography, and ASR behavior vary. Version dictionaries/rules, record changes, and re-evaluate on newly reviewed examples before broadening labels or changing thresholds.
8. **Keep call-type labels separate from graph inference.** They may help analysts filter speech but never establish a radio contact or network relation. Directed `RADIO_CONTACT` candidates continue to require explicit addressing and remain pending review.

## Current implementation status

The package implements deterministic overlapping labels for `fire`, `police`, `ems`, `bus`, `school`, `traffic`, `electrical`, `public_works`, `hazmat`, and `weather`, plus `unclassified`. The `call-types` command reports aggregate counts. These are keyword-based triage labels with no calibrated confidence, evidence span, or per-label review state. The local neural engine now emits versioned, evidence-checked proposals, but model self-reported uncertainty and agreement with keyword rules are not validation. Neither path is empirically validated against an adjudicated corpus and neither should be presented as reliable incident classification. This limitation is a release gate, not a claim about corpus accuracy.

The task definitions and synthetic positive/negative examples are recorded in the [radio call-type annotation guide](call_type_annotation.md). The guide clarifies the operational subject, excludes incidental location/address matches, and specifies an empty-label outcome for acknowledgments, routine status, and unsupported fragments. It remains a proposed annotation protocol until authorized reviewers adjudicate a sample.

## Suggested next research milestone

Before extending the taxonomy or automating decisions, define the label ontology and annotation protocol, then build a small adjudicated benchmark from authorized, TRANS-reviewed data. Store benchmark material and any private transcripts only in approved private storage; commit the label guide, synthetic examples, rule version, and aggregate evaluation report without source text or identifying metadata. Compare current rules against that benchmark and decide whether keyword rules remain fit for analyst triage.
